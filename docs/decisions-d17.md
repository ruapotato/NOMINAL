# D17. Break-fix: the OS is the game

This supersedes D16 and everything downstream of it. The station, the segments,
the tenants, the economy and the patch panel are deleted. Keep the C core, the
language, the VM, the VFS, the shell, determinism, headless and the TCP
protocol. Those were never the problem.

## Why the last design failed

I built a physics simulation about power and heat and put a terminal in front
of it. The OS was a *view onto* the game, not the game. So getting better at
the OS was never the same thing as getting better at the game, and every panel
in the desktop was decoration. Playtest verdict, and it was correct: "a DE full
of shit, no direction, no goal."

The four premises I proposed to replace it were each a known genre wearing an
OS costume — Robocode+OS, Zachlike+OS, Hacknet+OS. Same error, new hat.

## The premise

From how break-fix was actually taught at Novell: a script breaks an
installation, you get the ticket, you fix the install.

> A machine won't boot. The ticket says something vague, because real tickets
> are vague. You boot a rescue image, mount the broken root, `chroot` into it,
> walk the boot chain to find which stage fails and why, fix or reinstall what
> is broken, and boot it for real to prove it.

The OS is core because every verb is an OS verb, and because **the content is
generated by breaking a real system rather than authored as a fault table**.

## The one commitment that makes it real

**The boot must be simulated, not narrated.**

Every stage reads specific files out of the VFS and fails as a *consequence* of
what it finds there. The breaker corrupts a file; the failure follows from the
corruption. There is no fault ID, no symptom table, no mapping from "fault 7" to
"message 7".

The test of this, and it is a gate: **an arbitrary corruption of any file the
boot chain reads must produce a coherent failure without anyone having written
a case for it.** If I have to add a branch per breakage, the design has already
collapsed into the lookup table I am trying to escape.

## The boot chain

| stage | reads | fails as |
|---|---|---|
| firmware | partition table, boot sector | no bootable device |
| bootloader | `/boot/zbl/zbl.cfg`, kernel, initrd | syntax error, missing kernel, bad `root=` |
| kernel | initrd image | truncated, bad magic |
| initrd | driver modules, root by UUID | cannot find root, drops to emergency shell |
| init | `/sbin/init`, `/etc/fstab` | missing, not executable, dangling symlink, fstab blocks on an absent device |
| services | `/etc/init/*.service` | a required unit fails, dependency cycle |
| target | — | login prompt: the machine is fixed |

Each stage emits console output in the machine's own voice. That output is the
player's primary evidence and it must be honest: it says what the stage tried
to do and what it got, never what is wrong.

## The package database

Every file on the system is owned by a package and carries an expected hash.

- `pkg verify` — which files differ from what their package shipped
- `pkg reinstall <name>` — put them back
- `pkg owns <path>` — what would I be reinstalling

This is the fix verb, it is the real one, and it is why the breaker may corrupt
anything at all and the machine stays solvable. It also gives the player a
reason to reason about *scope*: reinstalling a package is a bigger hammer than
editing one line, and sometimes the bigger hammer destroys the local change
that was the only thing keeping the machine working.

## The rescue environment

A second, known-good root. Booting it gives a shell with the broken disk
present but not mounted. `mount`, then `chroot`, and now the tools inside the
broken system are the ones you are running. Getting this right — that `chroot`
changes which `/etc` you are reading — is most of the feel.

## The arc

1. **One machine.** A single fault, plainly visible in the console output. The
   naive fix by hand is correct and satisfying.
2. **A queue.** Tickets arrive. Faults start masking each other: fix the
   obvious one and a second is revealed underneath.
3. **Volume.** They arrive faster than you can chroot by hand, so you write
   triage scripts in NomScript. This is where the language earns its place —
   it is not imposed by a tutorial, it is forced by workload.
4. **A fleet.** Your real output is the script that fixes the machine before
   the ticket is filed.

That is "make yourself unnecessary", earned.

## Texture: Unix-shaped with alien corners

`ls`, `cat`, `ps`, pipes, permissions and `chroot` behave as a Linux admin
expects — fluency gets you in the door. The strangeness lives in what these
machines have accumulated: vendor packages, odd hardware, a driver that reports
in the wrong units. Curiosity gets you deep. (This keeps the best of D13.)

## Deleted

The station, segments, tenants, SLAs, the economy, the replicator, the
teleporter, the patch panel, rails and spines, the room view, the thermal and
power sim. All of it was the physics game.

## Kept

The C core and its build, NomScript, the VM and its instruction budget, the
VFS, the shell and pipelines, `man`, determinism and its four gates, headless,
the TCP line protocol, and the alien-device idea from D13.

## Why determinism matters more now, not less

A seed **is** a broken machine. That makes a failure reproducible, replayable
and shareable: "see if you can fix 4823." It also means the breaker can be
audited — I can prove a machine is solvable by solving it headlessly.
